# 情绪 agent 接受建议后自动调光更新包

## 这次已经接到哪里

本更新只接情绪监测页面，不改 AI 聊天页面。

正常使用流程：**情绪 agent 给出明确 CCT/照度 → 页面显示这组参数 → 用户点击“接受建议” → 后端自动调用已编译 SDK 桥接程序 → 自动计算配方并发送给唯一的灯。**

用户不用运行 Python 示例，不用打开师姐软件，不用编译，也不用再点“实验员已完成切换”。“暂不接受”不会发送灯控报文。5000 K / 300 lx 的示例已通过真实 SDK 和本地 UDP 收包检查，尚未在实灯上验证。

## 同事安装一次即可

1. 同事电脑需要 Windows x64、Python 3.10+、.NET Framework 4.7.2 或更新 4.x。主 agent 已有的 FastAPI、Pydantic、SQLAlchemy 环境继续使用，本更新不新增 pip 依赖。
2. 先关闭正在运行的主 agent 后端，将本 ZIP 完整解压。双击 `安装更新.cmd`，输入主 agent 项目根目录，也就是同时包含 `backend` 和 `fontend` 的文件夹。
3. 安装器先核对代码版本、校验更新文件，再备份需要替换的文件，并只安装必要文件；不接触 `.env`、API 密钥、主 agent 数据库或 AI 聊天代码。若同事已改过这些相关源码，安装器会列出冲突并停止，不会自动覆盖；将列出的文件交回适配即可，无需同事自行写调光逻辑。
4. 打开项目中的 `light_control/light_config.json`，把 `lamp_ip` 设置为这盏灯实际的 IPv4 地址。只填一个地址。原软件记录过 `.100` 和 `.101`，不能据此猜测现场地址。端口默认 `26666`，房间默认 `1`。已有灯具配置和已有标定会被保留。
5. 按原方式启动主 agent 后端，使用 **一个 worker、一个负责该灯的后端实例**。打开原来的“情绪监测”页 `/page/monitor`，按 `Ctrl+F5` 刷新页面。开始会话、生成新的建议并点击“接受建议”即可。

步骤 2–4 是首次部署设置，不是每次推荐后的操作。安装包已经有 exe、算法 DLL 和标定文件，同事无需 Visual Studio。安装器本身不启动开发服务器。

新建的 `strategy_lighting` 表会在后端原有启动流程中自动创建，不需要手工迁移或删除原数据库。安装前产生的旧建议没有数值目标，请生成新的建议。

如果需要定位备份，安装器会打印项目内 `.lumimind-backups/emotion-时间-编号` 的目录；其中只包含本次覆盖文件的原副本及安装清单。恢复时应先停止后端，再按相对路径恢复备份文件，不要删除原数据库。

## “推荐值”如何进入这个流程

需要特别区分：本次检查的本地旧情绪 agent 只会决定“切到调节光／切回办公光”，原本没有生成具体 CCT/lux 的优化算法。因此本更新添加了明确的 `recommended_lighting` 数据字段。

- 同事主 agent 已经产生具体推荐值时，应随原 `/api/model/emotion` 情绪上报一起传入 `recommended_lighting`。本更新从这个字段保存目标，接受时直接使用保存的原值，不从推荐文字、滑块或页面动画猜数值。
- 本地旧情绪 demo 没有提供数值时，自动使用 `light_config.json` 中的 `emotion_profiles`：调节光示例为 **5000 K、300 lx**，办公光示例为 **4500 K、300 lx**。这是可配置的接入演示参数，**不是根据情绪算出的最优处方，也不是本更新新实现的优化算法**。
- 若同事现有 agent 的推荐计算和接口与本地版本不同，需先适配其推荐值输出，不能把 demo 预设称作他的实时最优推荐。安装器的代码版本检查会避免盲目覆盖不同实现。

给维护同事的结构化数据约定（上游已输出 5000 K / 300 lx 的场景）：

```json
{
  "session_id": "demo_001",
  "timestamp": "2026-10-27T09:00:00+08:00",
  "emotion_label": "negative",
  "emotion_score": 0.1,
  "confidence": 0.99,
  "face_detected": true,
  "recommended_lighting": {"cct_k": 5000, "illuminance_lux": 300}
}
```

页面点接受时只自动提交 `session_id` 和 `strategy_id`。后端从数据库取出当时展示的那组参数下发，前端不能临时换成另一组参数。只在原情绪决策生成需要切换的建议时产生待接受目标；原冷却和“不切换”规则保留。

## 重复、失败与现场验证

- 一条建议只允许进入一次自动发送流程。重复点击、并发接受、重新发送同一个接受请求不会再次发送；成功后返回原执行记录。
- “暂不接受”持久化为拒绝；旧建议和已拒绝建议不可执行。发送中断、失败或结果未知时不会偷偷自动重试，避免灯具收到重复指令。
- 成功显示“已自动下发”，不是“实测已达标”。UDP 无本包可核验的灯具执行回执，实际 CCT/照度仍按你们的监测方式验证。
- 失败显示错误并退出弹窗。先核对 IP、网络、供电、SDK/标定和执行记录；解决后生成新建议。状态 `dispatching/unknown` 可能意味着指令已发送但结果未知，不能只凭刷新页面再次发送同一条建议。
- 随包是原编译包中的房间 1、2026-07-20 标定，尚未确认它对应当前单灯和测量位置。原标定如来自不同摆位或多灯组合，无法保证现场 300 lx；应换成当前单灯/测点的正确标定。安装器不会覆盖已有标定。
- 不要同时开多个控制后端或让师姐软件同时改同一盏灯，以免指令互相覆盖。

更多 SDK 参数、预计值含义及原软件位置见项目中的 `light_control/接入说明.md`。此次 ZIP 没有 `test_light.py`，也没有主 agent 的密钥和数据库。
